# UX refinement — September 6, 2026

## Mobile follow-up

The follow-up adapts both task shells to the visual viewport when the software keyboard changes the available height, while leaving pinch zoom enabled. Chat accepts multiline text. Navigation fits 320px screens, respects safe-area insets, and becomes compact in landscape. The document enables viewport-fit=cover.

Opening a catalog place now preserves the expanded list, search, and scroll position for return. Mobile place details use the available map region, have sticky close/save controls, and provide 44px minimum buttons. Short-screen discovery preserves a usable scroll region instead of letting secondary context consume the panel.

## Scope and direction

Refine the existing Caribbean tourist and Spotter experience, preserving the new population, photos, photo viewer, directions, map photo pins, verification tiers, and access-code authentication. No seed runs, deployments, migrations, or payment/verification actions were performed for this pass.

Impeccable's polish guidance informed the priority order: task failures and permissions first, then feedback, touch targets, and visual hierarchy. The incumbent teal/ocean/sand interface is the visual authority. The older DESIGN.md describes a different visual system; its detector findings against retained 9–14px metadata, rounded controls, and existing photo-viewer colors are contextual false positives for this refinement, not authorization to replace the current brand. No detector rules were suppressed. New trip headings, controls, and inputs use larger, legible steps.

## Implemented

- Map questions have an explicit, labeled send button with disabled/busy states. Category filters use consistent line icons and expose their selected state.
- Mobile discovery has a visible Browse/Map label; empty searches offer a direct clear-search recovery action.
- Chat has a labeled 44px send control, a 16px input to avoid mobile focus zoom, visible keyboard focus, and an announced waiting state that explains source checking.
- Plans have a clear page heading, readable trip titles, chronological rows with wrapping place names, and larger controls. Trip-day and pace selections expose their state; the trip-description input has an accessible name.
- Deletion asks for confirmation, waits for server success, disables duplicate actions, and retains the trip on failure with an actionable error.
- Spotter permissions load on arrival, not only after visiting Profile. Read-only accounts cannot start capture, accept missions, confirm places, or upload photos through the interface. Both missions and map explain the restriction without labeling the site a demo. Switching account logs out before returning to sign-in.
- Spotter language initialization respects a saved preference; changing language no longer gets overwritten by a subsequent profile response. Navigation uses explicit readable active/hover/focus colors.

## Follow-ups, not claims of completion

- This was a local tourist/Spotter UX pass, not a deployed-site audit or a new validation of the business/admin and paid mission lifecycle.
- Mission acceptance, on-location capture, second-person verification, payouts, email delivery, and native-device permissions were not exercised with real-world consequences.
- Existing saved itinerary data includes a 02:25 stop. The UI accurately preserves it; itinerary-time validation deserves a separate functional check before presenting that particular trip.
- Share currently hands off to WhatsApp. Native sharing/copy-link fallback, durable tab/deep-link navigation, and comprehensive modal focus management remain useful next improvements.
- Some older profile/mission metadata still uses small type. This pass prioritized the main task controls and plan readability; it is not a full accessibility-conformance claim.
